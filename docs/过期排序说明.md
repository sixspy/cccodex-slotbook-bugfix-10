# 过期排序说明（占位单）

日期：2026-11-22　状态：**已钉死，当日不得改口**

## 缺陷

占位单列表原排序键为 `holds.created_at`（创建时刻）。续期只改 `expire_at`、不改
`created_at`，于是越早创建、越快过期的占位反而沉底，运营按列表续错单。

## 钉死方案：甲路径（排序键同事务校正 + 物化序键）

正确性口径**只走**下列一种：

> **甲路径**：读列表前，在**同一事务**内按过期时刻重排，并把结果物化成序键；
> 事务失败则列表滚回上一次已物化的旧序。

不得混用乙路径（先写排序影子表再原子切换列表物化序）。本仓不存在、也不得新增
“排序影子表 + 原子切换”代码。**禁止只在前端排序糊弄**——前端只展示后端已物化的
`order_seq`，不做任何兜底排序。

### 排序键

```
ORDER BY expire_at ASC, id ASC
```

- 主键：过期时刻 `expire_at`（ISO 字符串，可直接字典序比较）。
- 同刻：以 `id` 升序稳定收口，保证同等输入永远得到同一序列。

### 物化

- 表 `hold_order(hold_id PK, order_seq UNIQUE, expire_at, materialized_at)`。
- `order_seq` 从 1 连续递增，与 `expire_at`、`id` 一一对应，落库后可核。
- 触发点：`GET /api/holds`（读列表前，同事务）、`POST /api/holds/renew`
  （续期改过期时刻后，同事务），以及会新增占位的 `POST /api/holds` 与
  `POST /api/waitlist/promote`（同事务）。各处都调用 `db.materialize_hold_order`，
  不另起口径。

### 失败回滚

- 物化任一步失败：事务回滚，`hold_order` 保持上一次提交的旧序，列表按旧序返回，
  响应 `fresh=false`，并单独记一条 `holds_reorder_fail` 审计。
- 抢档锁失败（争用）：不重排、不物化，返回旧序，响应 `fresh=false` 且
  `contended` 列出被争用的档期编码；后到者只留 `contention_log` 争用痕，不改业务。

## 并发：两人同时续期与刷列表

- 续期先抢**该占位所属档期**的档锁 `slot:<代码>`；刷列表因重排物化是全表口径，
  先抢**列表中各档期**的档锁。
- 后到者：锁定失败 → 只写 `contention_log`（动作“争用”，详情记持有者）→ 不改
  `expire_at`、不改 `order_seq`；续期返回 409，刷列表返回旧序且
  `fresh=false`、`contended=[...]`。
- 为此 `locks.try_acquire` 在返回失败前先提交争用痕，避免随后业务异常回滚把争用
  记录一并吞掉。

## 五处同态

下列五处必须展示同一序列（`order_seq`）与同一过期时刻：

1. 占位页列表序（`GET /api/holds`，`sort=expire_at`、`scheme=甲-…`）
2. 过期时刻（列表返回的 `expire_at`，即排序主键）
3. 续期入口（`POST /api/holds/renew`，改完同事务重排物化）
4. 对账页（`GET /api/reconcile` 的 `holds` 与 `order_ok`）
5. 审计页（`GET /api/audit` 的 `holds_order`）

## 偏航记法

任何下列行为记为**过期排序偏航**：只改前端排序；改回 `created_at` 作排序键；
甲/乙两路径混用；续期或刷表绕过档锁；命中争用仍改业务；跳过失败测直接改文案。
